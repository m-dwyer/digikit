# Digitakt II 1.15C SHARC SPI2 frame completion

This is a version-scoped cross-check for the open SHARC SPI2 path in
[`docs/FINDINGS.md`](../FINDINGS.md#the-sharc-side-of-the-spi-frame-link-vo).
All addresses below refer only to the Digitakt II 1.15C image named at the top
of that file. They come from a separate static analysis and are therefore
**[D]** here until reproduced in this repository. They must not be carried
into 1.16 by address alone.

## Result

On 1.15C, the `0xabc` argument passed into the SPI2 setup becomes the geometry
of two circular RX descriptors and two circular TX descriptors:

```text
ColdFire DSPI2
  -> SHARC SPI2 RX PDMA
  -> 0x00265210, then 0x00264210, repeating
  -> RX count-complete interrupt
  -> ADI_SPI_EVENT_RX_PROCESSED (0x20)
  -> callback 0x001c7748
  -> toggle bit 0 of DM[0x00261c94]
```

Every descriptor has `XCount=0x55e` and `XModify=2`, so each transfer is
exactly `0x55e * 2 = 0xabc` bytes. Configuration word `0x00100000` requests
an interrupt when X count expires.

## Setup and descriptor lists

The setup path is:

```text
0x001c8034  R4 = 0xabc
0x001c8036  call 0x001c7b68
0x001c7ba8  call 0x001c9f69  ; adi_spi_Open, device 2
0x001c7bb6  call 0x001c8fe8  ; adi_spi_RegisterCallback(0x001c7748)
0x001c7bf4..0x001c7c66       ; construct RX and TX descriptor lists
0x001c7c73  call 0x001c982f  ; adi_spi_DMATransceiver
```

The static transceiver object at `0x00261c98` selects descriptor-list mode
`0x4000`, two descriptors in each direction, RX head `0x002641a0`, and TX
head `0x002641d8`.

| Chain | Descriptor | Next | Start | Config | XCount | XModify |
|---|---:|---:|---:|---:|---:|---:|
| RX | `0x002641a0` | `0x002641bc` | `0x00265210` | `0x00100000` | `0x55e` | `2` |
| RX | `0x002641bc` | `0x002641a0` | `0x00264210` | `0x00100000` | `0x55e` | `2` |
| TX | `0x002641d8` | `0x002641f4` | `0x00267210` | `0x00100000` | `0x55e` | `2` |
| TX | `0x002641f4` | `0x002641d8` | `0x00266210` | `0x00100000` | `0x55e` | `2` |

## Completion and active-buffer selection

The selector at `DM[0x00261c94]` is zero-filled before startup. The first RX
descriptor fills phase 1 at `0x00265210` while phase 0 remains active. On RX
completion:

1. SPI2 RXDMA interrupt 70 reaches `SPI_Rx_Handler` at `0x001c9c0b`.
2. It calls `CommonDMAHandler` at `0x001c99ec`.
3. The common handler invokes the registered callback with
   `ADI_SPI_EVENT_RX_PROCESSED` (`0x20`).
4. Callback `0x001c7748` toggles selector bit 0, making the completed phase
   active while PDMA fills the other phase.

Resolver `0x001c771e` uses the selector to return the active RX base and its
paired TX base. The audio path then copies `0x802` bytes from the active RX
image to the local snapshot at `0x002558dc`.

This agrees with the ColdFire call already documented in `FINDINGS.md`:

```text
0x400cf9c4(0x802, 0x80005348, 0xabc, 0x8000488c)
```

ColdFire supplies `0x802` bytes of state and pads the outgoing DSPI2 frame to
`0xabc`; the SHARC receives the complete frame before activating it, then
copies the `0x802`-byte state portion for local use.

## Retargeting this result to 1.16

The 1.16 equivalents should be established by structure and dataflow:

- follow the relocated SPI2 setup after the `R4=0xabc` call;
- identify two circular RX and two circular TX descriptors with
  `XCount=0x55e`, `XModify=2`, and the X-count interrupt configuration;
- follow SPI2 RXDMA interrupt 70 through the common handler to an event-`0x20`
  callback;
- locate the zero-filled selector, its completion-time toggle, and the
  selector-based active-buffer resolver; and
- confirm the later `0x802`-byte copy into a local snapshot.

Until those edges are reproduced, this closes the receive-completion and
double-buffering path for 1.15C only. It does not establish 1.16 addresses,
field meanings, hardware timing, or the meaning of the SHARC-to-ColdFire
return content.
